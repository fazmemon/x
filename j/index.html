AI artifact taxonomy — one-pager skeleton

A SKELETON, not a finished doc. The engineer fills every ⟨placeholder⟩ with the team's real artifacts and rules, then compresses to one page. Purpose of the final doc: let anyone on the team route any artifact to the right production lane, so artifact/handover/standards work scales without every document being hand-written — and without AI output shipping unreviewed.

The three lanes

Lane 1 — Deterministic automation (templates + variables)

Definition: the artifact is fully determined by structured inputs — same variables, same output, every time. Rendered by a template engine (Jinja2/Ansible), never free-typed.
Routing test: could a diff review alone approve it? If yes, it belongs here.
AI's role at run time: none. (AI may have built the template once — that's Lane 3.)
Review model: PR diff of variables, not prose review.
Named failure mode: hand-editing rendered output instead of fixing the template/variables — the artifact silently forks from its source.
Team examples: ⟨device configs from SoT, port/patching sheets, standard MOPs, interface descriptions…⟩

Lane 2 — AI-judgment artifacts (draft → engineer owns)

Definition: every instance is unique and needs engineering judgment to be correct — design docs, handover docs, incident narratives, standards prose, review summaries. AI drafts; a named engineer verifies and owns it.
Routing test: would two competent engineers produce meaningfully different documents? If yes, it belongs here.
AI's role at run time: drafting, restructuring, gap-spotting — never the final authority on a fact.
Review model: a named owner is accountable for every claim; AI-drafted provenance marked ⟨how — footer tag? commit trailer?⟩.
Named failure mode: plausible unreviewed prose shipped as fact — fabricated detail survives because it reads well.
Team examples: ⟨handover docs, RFC/design docs, post-incident reports, standards pages…⟩

Lane 3 — AI as toolmaker (build once, run in Lane 1)

Definition: the deliverable is a tool — a generator, validator, drift-checker, parser — that AI builds once; the tool then produces artifacts deterministically (i.e. its output lives in Lane 1).
Routing test: is the same document produced repeatedly with different inputs? Then stop drafting it and commission the tool.
Review model: tool code reviewed once + accepted against known-good cases; after that, only its inputs are reviewed.
Named failure mode: trusting a tool that was never run against known-good/known-bad acceptance cases.
Team examples: ⟨config renderer from YAML SoT, pre/post-change diff checker, LLD table generator…⟩
